# Instructions for the marketing site redesign

Applies to every PR in the redesign (`docs/plan.md`). General repo rules stay in `docs/agent.md`; this file adds the rules specific to the public site and to how this project is run. Where both cover a topic, `docs/agent.md` wins and this file links to it.

## 1. Before you start a PR
1. `git fetch origin && git checkout main && git pull --ff-only`. Other agents push to main; always branch from the latest main.
2. One PR at a time. Do not open the next phase PR until the previous one is merged.
3. Check `git status`. Never discard or overwrite uncommitted changes you did not make.
4. Read the matching section of `docs/plan.md` and the public copy rules in section 6 below.

## 2. Architecture
- Marketing, docs, blog, legal and pricing pages are server components outside `app/(app)/`. Never import next-auth into them; use `lib/billing/access.ts` for checkout gating (see `docs/agent.md`, Billing).
- Shared marketing components go in `app/components/site/`. The app shell (`app/components/shell`) and app UI kit (`app/components/ui`) are reused, not forked. If a primitive fits both, put it in `ui`.
- Marketing tokens are new `@theme` names (`navy-*`, `accent-*`, `surface`, `bg-canvas`). Do not redefine `brand-*` or zinc values; the app depends on them, and its dark mode lives under `.app-scope` only.
- Page content that is long or reused (FAQ entries, feature lists, changelog entries, solution examples) lives in typed data modules (`lib/site/*.ts`) or Markdown (`content/`), not inline JSX, so tests can scan it.
- New marketing pages use `SitePage`, `PageHero` with `Breadcrumbs`, and `pageMetadata({ path, title, description })` from `lib/site/meta.ts` (canonical, Open Graph and X). Add the file to the publicContent file list, the sitemap, and a test that runs `checkHref` from `tests/helpers/links.ts` on every link.
- Never move or rename `/legal/*`, `/sdk.js` and other customer scripts, `/api/*`, `/signin`, `/share/*`, `/invite/*`, or app routes. New public URLs that differ from existing ones get a 301 in `next.config.js` redirects.
- No new runtime dependencies without a reason written in the PR. Diagrams are inline SVG or HTML/CSS; reuse `app/docs/_components/Diagrams.tsx` where possible.
- Every new public route exports `metadata` with a unique title and description, and is added to `app/sitemap.ts`.

## 3. Coding standards
- TypeScript strict, no `any` without a comment. Semantic HTML: one `h1` per page, headings in order, `nav`, `main`, `section` with `aria-labelledby`.
- Accessible by default: visible focus, keyboard-operable menus (Escape closes, focus returns), `aria-expanded` on toggles, 44px touch targets, WCAG AA contrast (see plan 5.2; white text on #16A36A is not allowed below 24px).
- Responsive: check 390px, 768px and 1280px for every page. No horizontal scroll at 390px.
- Images through `next/image` with width, height and alt text. Mock UI is wrapped in `SampleDataFrame` with the visible label "Example data".
- Respect `prefers-reduced-motion`. No autoplaying animation loops on marketing pages.

## 4. Testing and build
Run before every push that should be green, and always before opening or merging a PR:
```
npm run lint && npm run typecheck && npm test && npm run build
```
- `npm test` and `npm run build` regenerate `sdk-src/last-build.json`. Revert it before committing: `git checkout -- sdk-src/last-build.json`. Never commit `public/sdk.js` changes unless the SDK itself changed.
- Add each new public page or content module to the file lists in `tests/publicContent.test.ts` (internals, roadmap and hosted-only rules) and, where it states numbers or plan facts, to `tests/publicCopyMatchesApp.test.ts` or `tests/claimsAudit.test.ts`.
- New navigation gets a test that every href resolves to an existing route or a redirect.
- Docs-only PRs still run the full suite in CI.

## 5. Git and PRs
- Author every commit as `I m r a a n <2376086+ranababu1@users.noreply.github.com>` (`git config user.name "I m r a a n"`, `git config user.email "2376086+ranababu1@users.noreply.github.com"`).
- No AI attribution anywhere: no Co-authored-by trailers, no "generated by" lines in commits, PR titles, PR bodies or code comments.
- Conventional Commits (`docs: ...`, `feat(site): ...`), imperative, under 72 characters.
- Push the branch often: after each file change that leaves the build green, and at least every ~50 lines of production code. Never leave a pushed branch undocumented; the PR body says what is done and what is next.
- Open the PR, wait for CI (check and wordpress-plugin jobs) to pass, then merge with a merge commit (not squash, not rebase).
- Never force push, never rewrite pushed history, never push to main directly, never `reset --hard` or `clean -fd` a tree with someone else's changes.
- Never commit secrets, `.env*`, database files (`data/`, `*.db`), backups, `.next/`, `node_modules/` or build output. `.gitignore` covers them; check `git status` before committing.
- Database migrations (if a phase ever needs one): next index in `drizzle/`, and its `when` in `drizzle/meta/_journal.json` must be greater than the last entry (currently 1793500000000), or the migrator skips it.

## 6. Public site copy rules
These override the brief where they conflict.
- No internals on public pages: framework, database, hosting provider, env var names, rate limiter details, hash function names, repo or GitHub links, the admin console. (`tests/publicContent.test.ts` enforces most of this.)
- Hosted service only. Never offer or imply self-hosting, open source or on-premises, and do not use the word "hosted" in contrast to it.
- Never claim a feature, integration, certification or guarantee the app does not have. Unbuilt features appear only as Coming soon rows on /pricing. No public /roadmap page, no "Phase", sprint, milestone or date-promise wording on public pages.
- Statistics copy follows the code: sequential test (mSPRT) decides winners, Wilson intervals per variation, chance to beat control, SRM check. Do not present the z-test as the method; it is only an API field.
- Pricing copy follows `lib/plans.ts`, `lib/entitlements.ts` and `lib/billing/config.ts`. Never say Free is unlimited, a trial or includes everything. Do not say paid checkout is live until production has the payment settings.
- No invented customers, logos, testimonials, ratings or usage numbers. Sample data is labelled "Example data".
- No competitor names on non-blog public pages (tests enforce a list).
- Writing: plain, specific, short sentences. No em dashes. Avoid AI-sounding words (for example: seamless, effortless, unlock, supercharge, leverage, elevate, empower, robust, cutting-edge, game-changer, revolutionize, delve, harness, journey as a metaphor, "in today's fast-paced"). No exclamation marks in headlines.
- Blog: no in-body byline lines (`tests/blogByline.test.ts`); keep the wide blog layout and post header.
- Links from the signed-in app to public pages open in a new tab (`tests/inAppLinks.test.ts`).

## 7. Documentation on every change
As in `docs/agent.md` "Required on every change": add a top row to `docs/changelog.md` (commit "pending", IST time, summary; fill the hash in the next PR), update `docs/currentstate.md`, and tick the item in `docs/plan.md` section 6.
